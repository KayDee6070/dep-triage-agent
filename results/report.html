Dependency triage agent — evaluation report

Does tool routing actually help? Measured against two deliberately unintelligent baselines.

This is a development measurement, not the final result.Split: dev. The held-out task set has not been run; it is reserved for a single final measurement. Numbers here were used to diagnose behaviour and may freely have been iterated against, so they carry no claim of being unbiased.
Two held-out probes (minsafe-deep-03, minsafe-deep-04) were exposed during development and are permanently excluded from the final measurement.

The baselines are not weak opponents.no_agent calls every tool on every package and lets the model answer once, so it always holds strictly more information than the routing agent. Routing is therefore dominated whenever calling everything is affordable and fits in the context window. That is arithmetic, not a property of this task set, and the task set was deliberately not redesigned until the agent won.

Under injected tool failure

Each tool result is corrupted one way per run: an HTTP 503, a valid-but-empty payload, or a record with the field the answer depends on removed. This is the one condition the baselines structurally cannot compete in — both are single-shot scripts and cannot retry, switch tool, or abstain.

What this cannot tell you

  • Sample size. Twenty development tasks carry roughly ±15 percentage points at 95% confidence. More tasks is not the fix: eighty reaches only about ±11.
  • One model, one domain. Nothing here generalises beyond this model on Python dependency triage.
  • Reproducibility is partial. Greedy decoding with a fixed seed did not make every metric deterministic; one baseline is not repeatable run to run, and the observed variance is published rather than smoothed.
  • Correct under a fault is not verified recovery. A system can reach the right answer without having noticed the failure at all.
